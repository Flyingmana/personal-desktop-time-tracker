# Design: Internal Data Structure

## Approach

- Introduce a pure domain model in a new `TrackerData.kt` file in the root application package.
  It owns all tracked time and labels in one `TrackerData` value; Compose state and future storage
  are consumers of that value rather than owners of separate copies.
- Replace the provisional reporting-only `WorkEntry` type with a sealed `TimeEntry` hierarchy. A
  common interface gives reporting and day queries access to an entry's identity, start timestamp,
  and optional end timestamp, while concrete types keep regular-task and attendance-only fields
  distinct.
- Keep timestamps as `LocalDateTime`, matching the existing application and user-facing
  requirements. The app boundary obtains the current time and supplies it to pure domain
  operations; the model never reads the clock itself.
- Represent all references with `UUID` values. A UUID is generated by the caller and supplied to
  the creation operation, keeping transformations deterministic and providing stable identities
  for a future persistence adapter.
- Use immutable lists and data classes. Every operation returns a new `TrackerData`; the Compose
  root holds the current instance in `mutableStateOf` and replaces it after a successful operation.

## Data Model

```kotlin
data class TrackerData(
    val entries: List<TimeEntry> = emptyList(),
    val labels: List<TimerLabel> = emptyList(),
)

sealed interface TimeEntry {
    val id: UUID
    val start: LocalDateTime
    val end: LocalDateTime?
}

data class TaskTimerEntry(
    override val id: UUID,
    val text: String,
    override val start: LocalDateTime,
    override val end: LocalDateTime? = null,
    val labelIds: Set<UUID> = emptySet(),
) : TimeEntry

data class AttendanceEntry(
    override val id: UUID,
    override val start: LocalDateTime,
    override val end: LocalDateTime? = null,
) : TimeEntry

data class TimerLabel(
    val id: UUID,
    val name: String,
    val colorCode: String? = null,
    val parentId: UUID? = null,
)
```

`TaskTimerEntry` holds only label IDs, never copied `TimerLabel` objects. Attendance entries have
no task text or labels. A running entry has `end == null`; a finished entry has a non-null end
that is later than its start.

The order of `entries` is insertion order and is the model's deterministic default presentation
order. Callers may sort query results for a particular view without changing stored order.

## Domain Operations

Expose small pure functions that accept all changing inputs and return either the new model or a
domain error. A sealed `TrackerDataResult` avoids silently ignoring failed starts/stops and keeps
validation testable without Compose.

```kotlin
sealed interface TrackerDataResult {
    data class Success(val data: TrackerData) : TrackerDataResult
    data class Failure(val reason: TrackerDataError) : TrackerDataResult
}
```

The initial operations are:

- `startTaskTimer(data, id, text, startedAt)`: rejects blank text and duplicate IDs; appends a
  running `TaskTimerEntry`.
- `startAttendance(data, id, startedAt)`: rejects duplicate IDs and rejects the request when any
  `AttendanceEntry` is running; appends a running `AttendanceEntry`. Resuming attendance uses this
  same operation and creates a new interval.
- `stopEntry(data, id, endedAt)`: locates a running entry, rejects missing/already-finished IDs and
  end times at or before the start, then replaces only that entry while retaining its identity and
  immutable fields.
- `assignLabels(data, taskEntryId, labelIds)`: requires a task entry and existing label IDs, then
  replaces the entry's label-ID set atomically.
- `createLabel(data, id, name, colorCode, parentId)`: rejects blank names, duplicate IDs, missing
  parents, cycles, and a parent chain that would exceed three levels.

Operations outside this story, such as renaming/deleting labels or editing completed intervals,
will not be added prematurely. Their stories can extend this API with explicit validation rules.

## Queries

Queries are pure read-only functions over `TrackerData`:

- `entriesStartedOn(data, date)` returns all entries whose `start.toLocalDate()` equals `date`.
- `finishedEntriesOverlapping(data, startDate, endDate)` returns finished entries whose interval
  overlaps the inclusive date range. Running entries are excluded, preserving the reporting-page
  contract.
- `runningEntries(data)` and `runningAttendanceEntry(data)` provide direct state for timer UI and
  attendance controls.
- `labelsFor(entry, data)` resolves a task entry's label IDs against the label catalog. Missing
  references are not expected because mutation validation prevents them; the function remains
  defensive and returns only resolvable labels.

The reporting logic will consume `finishedEntriesOverlapping` and continue to split durations
across calendar days. This data-model story does not define total calculations or report display.

## Integration Plan

1. Add `TrackerData.kt` with the domain types, result/error types, operations, and queries.
2. Add focused Kotest coverage for valid operations, each rejection path, label hierarchy depth,
   label association, day lookup, and finished-range lookup.
3. Replace `WorkEntry` in `ReportingPage.kt` with `TimeEntry`/the query API and adapt the existing
   reporting tests. Its sample data becomes explicit `TaskTimerEntry` values.
4. Replace the temporary count state in `App()` with a single `TrackerData` Compose state value.
   Timer, attendance, label, and persistence stories will add their respective UI and adapters to
   this state holder.

No storage service, repository, serializer, file path, database schema, or I/O coroutine is part
of this integration. The data-persistence story will introduce an adapter that loads a
`TrackerData` at startup and saves updates produced by these operations.

## Edge Cases

- A regular task timer and an attendance entry may run concurrently; only running attendance
  entries are mutually exclusive.
- Two entries may share the same timestamp. Their UUIDs distinguish them and insertion order stays
  deterministic.
- A timer crossing midnight is selected by an overlapping report-range query. Per-day duration
  allocation remains reporting logic.
- A valid label can be assigned to many task entries, and a task may have no labels.
- The model does not repair malformed data loaded from a future storage layer. The persistence
  story is responsible for recovery; its adapter must either supply a valid `TrackerData` or apply
  a documented recovery policy before handing data to this model.

## Out of Scope

- Persistence representation, transactional write behavior, loading, recovery, storage partition
  selection, and backups
- UI controls, test tags, navigation, and live elapsed-time refresh scheduling
- Report totals, averages, and exact display formatting
- Editing or deleting finished entries or labels
